# Trace360

Mule account detection for PS-01: ingest bank statements in many layouts, score each account
with explainable rules and money-flow network analysis, link (synthetic) victim complaints, and
produce ranked leads with evidence reports.

- **Phase 1:** explainable rule indicators + money-flow graph (rings, centrality, money trail).
- **Phase 2:** unsupervised models on account-week windows: Isolation Forest (unusual weeks),
  SHAP (why a week was flagged) and HDBSCAN (behaviour roles). There are no fraud labels, so the
  models are evaluated with a synthetic-injection test, not accuracy: see
  [reports/model_evaluation.md](reports/model_evaluation.md).

## Layout

```
data/
  raw/          N_SOA.xls/.xlsx statements (gitignored, never committed)
  processed/    parquet outputs + stats.json (gitignored)
  synthetic/    generated complaints (gitignored)
backend/
  app/
    config.py               all thresholds and weights
    ingestion/              layout detector, one adapter per layout, narration parser, canonical schema
    features/               per-account features, account-week windows, 0-1 rule indicators + reasons
    graph/                  flow graph, Louvain rings, PageRank/betweenness, money trail
    complaints/             synthetic complaint generator + RapidFuzz matcher
    models/                 Isolation Forest, SHAP, HDBSCAN roles, evaluation; artifacts/ = trained model + model card
    scoring/                risk score (0-100), top-5 reasons, alerts / lead list
    reports/                evidence PDF (Jinja2 + WeasyPrint, ReportLab fallback)
    pipeline/run_pipeline.py
    api/                    FastAPI routes
  scripts/                  ingest.py, profile_data.py, train.py
reports/                    model_evaluation.md / .json (generated by scripts/train.py)
  tests/                    fixtures are built in code (no real data)
frontend/                   React + Vite + TypeScript UI (src/api + src/hooks = contract; pages/components = replaceable)
docs/                       FRONTEND_INTEGRATION.md, openapi.json (API contract), api_examples.md
Makefile                    setup / pipeline / api / web / dev / test
```

## Run the whole app locally

Needs Python 3.11+, Node 18+ (tested on Node 26) and `make`. On macOS, WeasyPrint needs Pango
(`brew install pango`); without it PDFs fall back to ReportLab automatically.

```bash
git clone https://github.com/sanjeevvr11/crimecoders.git trace360
cd trace360
make setup          # backend/.venv + Python deps, frontend npm deps
```

Put the 25 statements (`1_SOA.xlsx` … `48_SOA.xlsx` from `Proposed_Data_Randomized_Final.zip`) in
`data/raw/`. The `~$25_SOA.xlsx` lock file is ignored, and the data is never committed.

```bash
unzip -j Proposed_Data_Randomized_Final.zip -d data/raw
make pipeline       # ingest, features, graph, models, scores, evaluation report (~1 min)
make dev            # API + web app together; Ctrl-C stops both
```

| What | URL |
|---|---|
| Web app | http://localhost:5173 |
| API docs (Swagger) | http://localhost:8000/docs |
| Health check | http://localhost:8000/api/health |

Other commands: `make api` and `make web` (run separately, each in its own terminal), `make test`
(backend tests), `make typecheck` / `make build` (frontend), `make contract` (regenerate
`docs/openapi.json` and the frontend types after changing backend response models), `make examples`
(regenerate `docs/api_examples.md`).

### Manual commands (without make)

From `backend/`:

```bash
python3.11 -m venv .venv && .venv/bin/pip install -e ".[dev]"
.venv/bin/python scripts/train.py               # pipeline + models + evaluation report
.venv/bin/python -m app.pipeline.run_pipeline   # pipeline only

```

From `frontend/`: `npm install`, then `npm run dev` (:5173). The dev server proxies `/api` to :8000.

Outputs: `data/processed/*.parquet`, `data/processed/stats.json` and `data/trace360.duckdb`
(tables `transactions`, `accounts`, `account_features`, `window_features`, `indicators`, `edges`,
`nodes`, `rings`, `network_scores`, `complaints`, `complaint_matches`, `scores`, `reasons`, `leads`,
`alerts`, `window_scores`, `shap_reasons`, `account_anomaly`, `account_roles`, `role_profiles`).

## Frontend

`frontend/` is a plain React + Vite + TypeScript UI with eight screens: Overview, Leads, Money Trail,
Account, Network, Complaints, Models and Data. Overview opens with the conclusion of the whole investigation:
what each screen found, the accounts to act on with a next step for each, rings, the largest
account-to-account chains, a watchlist and the limits of the evidence. Money Trail (`/trail/:id`) is the investigation view: hop
columns of where money came from and went, animated transfers, cross-account and shared-counterparty
chains, and a hop-by-hop breakdown of the chosen chain. Data (`/data`) lets you upload more statements
(.xls, .xlsx or .csv in one of the supported layouts), check what Trace360 found in each, then add them to
the dataset or replace it and re-run the analysis; replaced or removed statements are kept in `data/archive/`
and can be restored. The UI is built so the UI can be replaced without touching the backend:
`src/api/` (generated types + client) and `src/hooks/` stay, while `src/pages/` and `src/components/`
can be swapped. See **[docs/FRONTEND_INTEGRATION.md](docs/FRONTEND_INTEGRATION.md)**, plus
`docs/openapi.json` and `docs/api_examples.md`.

## Sign-in and roles

Sign-in is on. The first `make dev` creates three demo users (admin, investigator, viewer) and
prints their passwords, which are also saved in `data/demo_users.txt` (gitignored). The app opens on
a login page; the sidebar shows who is signed in, their role and a Sign out button. Screens a role
may not use are hidden (Ingestion for non-admins; transactions, connection details and the evidence
PDF for viewers), and the API refuses them anyway. `TRACE360_AUTH=off make dev` switches sign-in off
(no login, masked for everyone, every screen usable).

| Role | Can do |
|---|---|
| viewer | read every screen, identifiers masked |
| investigator | also transactions, connections and evidence PDFs, still masked |
| admin | everything, identifiers **unmasked**, Ingestion, re-running the pipeline, users and the audit log |

- Create users: `make demo-users` (one per role, random passwords printed and saved to
  `data/demo_users.txt`, gitignored) or `make user USERNAME=asha ROLE=investigator` (prompts for the
  password). Or set `TRACE360_ADMIN_USER` / `TRACE360_ADMIN_PASSWORD` for a first admin.
- Users, sessions and the audit log live in `data/auth.sqlite3` (gitignored). Passwords are scrypt
  hashed; sessions are an httpOnly cookie valid 12 hours; 5 wrong passwords in 5 minutes block that
  user name from that address for a while.
- The audit log records sign-ins, account views, transaction and connection views, PDF downloads,
  uploads, pipeline runs and user changes, with whether the data was shown unmasked.
- Admins manage users in the **Users** tab: add a user (with a generated password), change role,
  deactivate / reactivate, reset a password, and read the audit log with user and action filters.
- Endpoints: `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`,
  `GET/POST /api/admin/users`, `PATCH /api/admin/users/{id}`, `GET /api/admin/audit`.

## How the data is handled

- **Layouts:** CRN statement (files 2, 4, 5; person-name headers, so D/C and CRN columns are found
  by content and position), debit/credit (6), ICORE short (7–9, 11, 12, 17–20, 22–24, 26, 28, 48),
  ICORE full (14–16, 25), misc ledger (1) and the 26-column extract (3, blank rows dropped, PAN never loaded).
- **Account identity:** one statement file is one subject account, `account_id = SOA<n>`. The
  account number is kept only where it is constant (files 2, 4–9) and is used solely to fold
  `acct:<number>` counterparties into subject nodes. Per-row account numbers are anonymised and
  never used for linking (files 26 and 48 share them as an artefact).
- **Time:** only ICORE `pstd_dt` is a usable timestamp (`time_reliable=True`). Every date in files
  1–6 and every `Tran_Date` is shuffled and is kept only as `raw_date`. Time features (dwell,
  bursts, night share) exist only for ICORE accounts.
- **Balances** are randomised and are never used.
- **Narrations:** real text only in files 2 and 4–9. The parser extracts channel and a typed
  counterparty key (`upi:`, `acct:`, `ifsc:`, `name:`). UPI VPAs are cut to their 11-character local
  part so that CRN-layout truncation matches ICORE. The `TXN-XXXXXXXXXX` tokens elsewhere contain
  channel codes only at the rate random strings would, so recovery from tokens is off
  (`RECOVER_CHANNEL_FROM_TOKENS`).
- **No labels, no complaints:** scores are rule- and network-based leads, not predictions.
  Complaints are synthetic, generated from real counterparties with typos and truncation, and
  labelled `synthetic=True`. "Dormant & Total Freeze" status is not treated as a label.

## Scoring

```
base = 100 × (0.65·indicator + 0.35·network)
risk = base + 0.30 · anomaly · (100 − base)
```

Weights, ramps and thresholds are in `backend/app/config.py`. `risk_score_phase1` (rules + network only)
is kept alongside for comparison.

- **Indicators** (each a 0–1 ramp, weighted mean over those applicable): pass-through ratio,
  fan-in, fan-out, small-credit/large-debit ratio, round-amount share, UPI share, fast outflow
  (credit value debited within 2 h), median dwell, burst hours, night share and transactions per
  active day.
- **Network:** shared counterparties with other subjects, PageRank (amount-weighted flow graph),
  weighted betweenness and ring membership. Rings come from Louvain (fixed seed) on the core graph
  of subject accounts plus counterparties shared by two or more of them.
- **Anomaly (uplift):** the Isolation Forest compares each week with all weeks and with the account's
  own usual week, so a consistently mule-like account is *not* unusual for itself. The anomaly score
  therefore only adds to the score, never subtracts. Accounts without reliable timestamps
  (SOA1–6) have no anomaly score and keep their base score; missing is never imputed as 0.

## Models (Phase 2)

| Model | Use in Trace360 |
|---|---|
| Isolation Forest | flags the most unusual 5% of account-weeks; account anomaly = mean of its top-3 calibrated week scores |
| SHAP TreeExplainer | top-3 plain-English reasons for each flagged week |
| HDBSCAN (weeks) | behaviour roles: collector / distributor / layering / normal-looking / unclassified |
| HDBSCAN (accounts) | roles for statements without timestamps (collector / distributor / normal only) |

Synthetic-injection results, stability, agreement with the rules, cluster quality and a Phase 1 vs
Phase 2 top-10 are in [reports/model_evaluation.md](reports/model_evaluation.md). In short: the
models are stable across seeds but drift over time (retrain when new statements arrive, which takes
under a second); they catch injected night bursts and round-amount layering far better than rapid
pass-through, because pass-through is the *normal* behaviour of the statements in this dataset.
